## 3. The nonce/CSP mechanism, end to end, and whether static assets can carry the same guarantees

### 3.1 Current mechanism

1. Nonce generation: per shell request, `randomBytes(16).toString("base64url")` in [routes.ts:72](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/routes.ts#L72); `randomBytes(18)` in [gateway.mjs:384](/Users/monkey/dev/jumpyBrain/integrations/macos-companion/gateway.mjs#L384). No nonce is ever persisted or reused across requests.
2. CSP header (both hosts, identical string): `default-src 'none'; script-src 'nonce-N'; style-src 'nonce-N'; img-src 'self'; connect-src 'self'; frame-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` ([routes.ts:73](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/routes.ts#L73), [gateway.mjs:385](/Users/monkey/dev/jumpyBrain/integrations/macos-companion/gateway.mjs#L385)). Note: no `'self'` in script-src/style-src and no `'unsafe-inline'` anywhere.
3. Nonce validation and application: [graph-page.ts:31](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/graph-page.ts#L31) rejects non-base64url nonces; the nonce is placed on the two inline `<script>` tags and the one inline `<style>` tag in the HTML.
4. Runtime reuse: the main inline script reads `document.currentScript.nonce` ([graph-page.ts:215](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/graph-page.ts#L215)) and passes it to `installExtensionsBrowser`, which sets `script.nonce = options.nonce` on dynamically injected extension scripts ([extensions-browser.ts:164](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/extensions-browser.ts#L164)). Those extension scripts are served same-origin by the gateway at `/companion/extensions/assets/<id>/<revision>.js` ([extensions-gateway.mjs:134-140](/Users/monkey/dev/jumpyBrain/integrations/macos-companion/extensions-gateway.mjs#L134-L140)) and currently *require* the document nonce to execute, because script-src has no `'self'`.
5. Enforcement tests: [test/server-http.test.js:74-140](/Users/monkey/dev/jumpyBrain/test/server-http.test.js#L74-L140) asserts the exact CSP shape (`script-src 'nonce-…'`, `style-src 'nonce-…'`, no `unsafe-inline`), that every `<script>`/`<style>` tag carries the nonce, that header nonce == HTML nonce, that `/`, `/?note=…` and `/graph` return byte-identical HTML after nonce normalization, and that no API key, title, body, root path or note id leaks into the shell (content-free property). [test/lexical-bundle.test.js:11-22](/Users/monkey/dev/jumpyBrain/test/lexical-bundle.test.js#L11-L22) additionally pins: the editor bundle is inlined in the HTML, the HTML contains **exactly 2 `<script>` tags, both with only the nonce attribute**, and `<style nonce=…>` is present.

### 3.2 Can externally served CSS/JS carry the same guarantees?

Yes, with one of two CSP options:

- **Option A (strictest, smallest CSP delta): keep `script-src/style-src 'nonce-N'` and put the nonce attribute on the external tags** — `<script src="/shell-assets/shell-abc.js" nonce="N">` / `<link rel="stylesheet" href="…" nonce="N">`. CSP nonces apply to external subresources as well as inline elements (they are stripped on redirects; there are no redirects on these routes). Because the HTML is server-composed per request anyway, embedding the per-request nonce on the tags is free. Caching still works if asset URLs are content-hashed (`cache-control: public, max-age=31536000, immutable`), because the cache key is the URL, not the nonce. This option changes **no CSP directive** and keeps the property "no script/style executes unless the server put this request's nonce on it".
- **Option B (precedent in-repo): add `'self'` for a build-emitted asset prefix**, exactly like the drawing frame: [drawing-assets.ts:10](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/drawing-assets.ts#L10) serves `/drawing-frame` + `/drawing-app/*` with `script-src 'self'`, an allowlist of only build-emitted files, path-traversal guard, ETag/304, immutable caching for hashed chunks, and a separate CSP scoped to that frame (`frame-src 'self'` in the shell CSP exists solely for it). Applying the same pattern to the main shell would mean e.g. `script-src 'nonce-N' 'self'` restricted in practice to `/shell-assets/*` (CSP cannot scope `'self'` to a path, so it would allow any same-origin JS — a real, if small, weakening of the XSS posture on a page that holds the API key in memory). Extension asset injection (which is same-origin) would stop needing the nonce.

Recommendation: **Option A for the first slice** (nonce on external tags; zero CSP string change; the pinned tests in 3.1 keep passing except the script-count assertion if scripts are added). Option B is only needed if you want to drop per-request nonces from asset tags or allow extension scripts without nonce; it must be documented as a CSP contract change in [docs/shared-memory-protocol.md](/Users/monkey/dev/jumpyBrain/docs/shared-memory-protocol.md) (the authoritative CSP reference, per [browser.docs.md "Non-responsibilities"](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/browser.docs.md#L124-L128)).

Either way, the serving mechanics should mirror [drawing-assets.ts](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/drawing-assets.ts): allowlist = files present in the build output directory, sha256 ETag, `immutable` for hashed names, `no-cache` for entry files, `nosniff`, GET/HEAD only. Today that logic is private to drawing assets; generalize it into a shared static-asset module used by both drawing and shell assets.

### 3.3 What must stay inline

- `themeBootstrap` ([browser-theme.ts:96-151](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/browser-theme.ts#L96-L151), comment at :95): runs in `<head>` before first paint to set `data-theme`/palette from localStorage and avoid a theme flash. Either keep it inline with the nonce, or move it to a blocking external head script with the nonce — do not move it to a deferred/async asset.
- The nonce itself is read from `document.currentScript.nonce` for extension script injection; if the main script becomes external, that read still works (the nonce attribute is on the external tag too).

## 4. Why inlining exists: deliberate vs incidental

Deliberate, documented:

- [docs/shared-memory-protocol.md:322-324](/Users/monkey/dev/jumpyBrain/docs/shared-memory-protocol.md#L322-L324): the `/` and `/graph` entrypoints "serve the same content-free, nonce-CSP-protected HTML shell… The Node package serves HTML, CSS, and locally bundled vanilla Lexical JavaScript under the nonce; no React, CDN, separate frontend service, or asset deployment is required." — i.e., single-package, no-asset-deployment serving is a stated product property, and the content-free shell (no key/path/title/body in HTML, enforced by tests in 3.1) is the security property the nonce exists to protect.
- [notes-browser.ts:10-11](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/notes-browser.ts#L10-L11): "String.raw keeps shell JavaScript readable; the Lexical surface is bundled separately." — readability of shell JS, with the heavy editor already bundled.
- [docs/build-footprint.md:237](/Users/monkey/dev/jumpyBrain/docs/build-footprint.md#L237): "retain inline safety, licenses, dependency separation, package ceilings"; [docs/build-footprint.md:381](/Users/monkey/dev/jumpyBrain/docs/build-footprint.md#L381): "deferring optional surfaces (map, feedback form, retained versions) out of the inline script… is an architecture change rather than a build setting" — the maintainers already know the inline script is heavy and classified moving things out as an architecture decision.
- [browser-theme.ts:95](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/browser-theme.ts#L95): head bootstrap under the nonce (see 3.3).
- Git history: the nonce CSP is present since the initial snapshot (`8eac9adf`, v0.3.1 beta) and was extended to dynamically injected extension scripts in `ba2cdf43` ("Add trusted executable desktop extensions"). So nonce-based inlining is original design, not an accident.
- Known gap that motivates the proposal: [src/architecture.docs.md "Boundary verification"](/Users/monkey/dev/jumpyBrain/src/architecture.docs.md#L97-L99) states the source scanner "is not a proof for computed imports, embedded browser scripts or native integration modules" — the ~4.6k lines of embedded CSS/HTML/JS are explicitly outside the architecture guard, ESLint and `tsc` type-checking of the strings themselves.

Incidental (not security- or packaging-driven):

- The 4 regex literals in [editor-markdown.ts:37-40](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/editor-markdown.ts#L37-L40) use `String.raw` for backslash-escaping only; they are not presentation and should be excluded from any extraction count.
- The `createDreamHandoff.toString() + String.raw…` construction in [dream-handoff.ts:112](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/dream-handoff.ts#L112) is a readability trick, not a security choice; it means at least one "script block" is generated from a function body and cannot be moved to a file verbatim.
- Per-view CSS/HTML blocks accumulated file-by-file as features landed (boards, drawings, dream, access keys, settings — see git log for those files); the split into `*-view.ts` markup/style modules vs typed controllers in [browser-entry.ts](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/browser-entry.ts) shows the intended direction was already "typed controllers + thin inline wiring" ([browser.docs.md:132](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/browser.docs.md#L132): "new logic belongs in typed modules").

Benefit:

- Up to 52 presentation blocks / ~4,645 lines leave the unlinted `String.raw` world. Realistic phasing: slice 1 ≈ 270 CSS lines; slice 2 ≈ +1,500 CSS lines; slice 3 ≈ +350 markup lines; slice 4 ≈ +3,000 JS lines (highest effort). After slices 1-3, [notes-browser.ts](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/notes-browser.ts) drops from 1,864 to roughly 550 lines; after slice 4, to ~20 lines of TS re-exports.

## 9. Risks / reasons NOT to do this

1. The single-scope coupling (2.2) means only CSS (and maybe markup) extraction is mechanical. If the main value is JS lintability, the project is a rewrite of how the shell boots, and the existing mitigation — typed controllers in [browser-entry.ts](/Users/monkey/dev/jumpyBrain/src/adapters/http-server/browser-entry.ts) with thin inline wiring — may already capture most of the benefit at lower risk.
2. CSP is a documented public contract ([docs/shared-memory-protocol.md](/Users/monkey/dev/jumpyBrain/docs/shared-memory-protocol.md)); Option B (`'self'`) weakens the nonce-only execution guarantee on the page that holds the API key in memory. Option A avoids this but keeps per-request nonces on asset tags, and any future redirect on an asset route would silently strip the nonce and break loading.
3. Tests and smokes are built around inline scripts (nine test files regex-extract the last `<script>`; [scripts/browser-shell-test-helpers.mjs](/Users/monkey/dev/jumpyBrain/scripts/browser-shell-test-helpers.mjs) parses function text out of it). Moving JS external breaks them all at once; keeping them green through the migration means maintaining two loading shapes for a while.
4. Caching semantics change: today the shell HTML is `no-store` at the gateway (and uncached-ish at the plain server); hashed immutable assets become permanently cacheable — an upgrade/rollback behavior change that the drawing frame already accepts, but the shell is loaded far more often, so a bad asset name strategy would be user-visible.
5. `themeBootstrap` must remain a blocking pre-paint script (3.3); a naive "extract everything" pass would introduce a theme flash.
6. Packaging gates are exact (`assert.deepEqual(packageBudget, …)` in [test/package-footprint.test.js:18](/Users/monkey/dev/jumpyBrain/test/package-footprint.test.js#L18)); any file-count/byte growth must be re-measured and explained in [docs/build-footprint.md](/Users/monkey/dev/jumpyBrain/docs/build-footprint.md), and `validateLocalPackFiles` must keep passing ([scripts/local-pack-manifest.mjs](/Users/monkey/dev/jumpyBrain/scripts/local-pack-manifest.mjs)).
7. The "content-free shell" property must be preserved for the new asset routes too: assets must be build-emitted and allowlisted (drawing-assets.ts pattern), never request-derived paths.

### What evidence would falsify the proposal

- If nonce-on-external-tags (Option A) does not execute in the pinned Electron 44 / Chromium targets (it should — standard CSP — but verify in slice 1 with `scripts/electron-smoke.mjs`), the strict-CSP path fails and the choice becomes Option B or nothing.
- If slice 1 cannot demonstrate byte-identical CSS (same rule set) between inline `<style>` and served `shell-<hash>.css` on the fixed-nonce `graphPageHtml` render, the "no-regression by construction" claim for CSS is false.
- If `npm run smoke:theme` screenshots differ beyond noise after slice 1, the composition order of the `<style>` block matters (cascade) and extraction needs per-block links in the original order rather than one bundle.
- If the packaging gates fail on slice 1 without a plausible measured explanation (e.g. hashed duplicate copies of CSS both inline and external), the footprint-neutrality assumption is wrong.
- If slice 4's scope estimate balloons (shared-scope identifiers turn out to cross-cut in ways that require redesigning the shell boot), the cost side of the proposal dominates and only slices 1-2 are worth doing.
