## Confirmed findings

### P1 — Idle companion polling closes search and Dream dialogs

**Confidence: high. Reproduced interactively and in an isolated browser regression.**

Steps:

1. Open the authenticated companion on a connected local brain.
2. Open Search from Home or the navigation bar.
3. Wait without clicking outside the dialog.
4. The dialog closes at the next ordinary companion poll, generally within approximately 750 ms. Typing a query may start a request, but closure aborts it. The failure reproduces without typing.

Dream's dialog also closes on the next poll. Its local-brain limitation message is therefore difficult to read. Inline-reference cancellation follows the same unconditional code path; its live impact was identified from the code, not by modifying a personal note.

Captured browser stack:

```text
HTMLDialogElement.close
closeSearch
companionLock
companionApplyState
companionPoll
```

In `src/adapters/http-server/companion-browser.ts:145`, `companionLock(value)` always calls `cancelReferenceInteraction()` and closes Search/Dream, even when `value` is false. The idle branch of `companionApplyState` calls it for each successful poll (`:207`); polling is scheduled every 750 ms (`:254`). This behavior exists in both the installed source and the current working tree.

Recommended correction: cancel interactions when actually entering a frozen/fenced state, preserving normal dialogs and reference interactions across unchanged healthy polls. Keep the existing save/switch barriers. Add a regression that leaves Search open across several idle polls and completes a query; cover reference suggestions and Dream too.

The existing companion smoke passes because it does not check a search dialog surviving idle polls. A temporary copy of that smoke with a 1600 ms open-dialog assertion fails:

```text
AssertionError: Idle companion polling must preserve an open search dialog
false !== true
```

Reproducer and output: `/tmp/jumpybrain-qa-20261016/companion-poll-regression.mjs` and `.log`. The temporary runner imports the installed runtime and uses synthetic profiles and documents.

### P2 — Memory map hides truncation warnings

**Confidence: high. Reproduced against the real brain.**

Steps:

1. Open Graph with no filters against a brain containing more than 500 notes.
2. Observe the successful map and its displayed count.
3. Compare the graph response's counts and warnings with the visible UI.

Observed payload:

```json
{
  "stats": { "documents": 1636, "nodes": 500, "edges": 421 },
  "options": { "limit": 500 },
  "warnings": ["Graph response was limited to 500 nodes."]
}
```

The UI shows `500 notes · 421 connections`, with no visible truncation warning or total-note count. The accessibility label says “Shown on this map,” but does not explain the omitted notes. A user can mistake the successful view for the complete brain.

`src/adapters/http-server/graph-page.ts:310` stores the payload and marks it loaded; `render` displays node/edge counts without presenting `warnings`. The same omission exists in the current working tree.

Recommended correction: show a concise partial-map message and a way to narrow the view, such as “Showing 500 of 1,636 notes. Filter to explore more.” Preserve the bounded graph response.

### Test maintenance — Daily-capture smoke expects outdated helper text

**Confidence: high. Assertion-only failure isolated.**

The installed `scripts/daily-capture-smoke.mjs:364` expects `/Enter to insert/`, while the current helper displays `↑ ↓ choose · Enter insert · Esc close · Index may be stale`. Both desktop and mobile reference cases fail at that assertion.

A temporary runner changed only that expectation to `/Enter (?:to )?insert/` and relocated imports to the installed runtime. All 15 daily-capture cases then passed, including the remaining reference behavior. The repository and installed script were left unchanged. Prefer asserting the intended accessible instruction or behavior without binding the test to this incidental wording.

### Usability observation — Narrow graph filter input

At 390 px, the graph title/tag filter has a total width of about 70 px because it shares a row with the 204 px Dream action and Filters. It remains operable and there is no horizontal page overflow, but only a short query is readable. Giving the search/filter field its own row would improve narrow-screen use. Filtering currently applies on change/blur or Enter, rather than every keystroke.
