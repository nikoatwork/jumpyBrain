# Named-subject candidate discovery — contract before new outputs

The previous [identity ordering follow-up](reports/2026-10-28-identity-v4.md) improved seen controls but failed both fresh confirmation sets. In its final three orientation tasks, required project introductions were absent from the existing pool. Keep those failures and the rejected policy outcome. This experiment asks whether bounded canonical-metadata discovery can admit missing named sources before final ordering. It does not infer current truth from a project name.

## Workload and separation

Retain all 210 pages / 124 tasks from v4 as seen regression controls. Add `discovery-confirmation/`: 15 fictional pages / 16 reserved tasks, giving **225 pages / 140 tasks**. The new families are Wrenfall seed exchange, Patchbay oral history collection, and Millrace volunteer water watch. Their tasks include orientation, source-plus-permission/physical constraints, copy integrity, decision rationale, historical intent, exact navigation, a literal phrase, two named subjects, and the deliberately shared alias Relay. Questions use varied workflow structures rather than a single four-question template. The pages have prose beyond the scored statements, separate source records and proposals, and explicit role/authority limits. They remain hundreds of words, not a large-document evaluation.

`build-discovery-confirmation.py` reproduces the fixture without reading run artifacts. Only each suite's `corpus/` is indexed. Queries/options and scoring-only `rubric.json` remain separate. Use the unchanged first-three guarded-expansion policy, five compact results, 8,192 bytes per response and 32,768 total response bytes; count all recall/read requests, metadata and errors with the pinned tokenizer. Rich search is a separate page-finding track and must not select expansion reads.

A dedicated fixture-author agent creates sources/questions/rubrics without candidate policy outputs. Another agent implements policy and deterministic tests without inspecting fresh run outcomes. The parent executes paired runs and source-checks every changed fresh result and every loss. These are different agents in the same model-assisted process, not independent human adjudication or a blinded user sample. All committed old holdouts and the new confirmation cases become seen after this comparison. Do not tune on fresh outputs or add another confirmation extension within this investigation.

## Frozen arms

Run the unchanged runtime first, then two separate eval-only arms against the same runtime/input hashes:

1. `baseline`: unchanged retrieval, with observation hooks only.
2. `discovery`: bounded canonical-title/alias/tag subject recognition admits at most eight missing named files before the existing final-pool ordering. Newly admitted candidates have score zero; original candidates are preserved. No body inference, corpus-specific names, gold access, model, new state or index is introduced. The hook implementation and policy file hashes identify the precise admission point, eligibility/bypass rules and bounded repair behavior.
3. `discovery-identity`: the same discovery mechanism followed by the existing unchanged `identity-policy.mjs` ordering. This is a declared combined arm, not a post-result rescue. The earlier identity-only v4 result remains rejected.

Freeze exact policy, hooks, runner, all corpus/query/rubric inputs and complete source/compiled runtime identity before the first new quality output. Preserve all arms and every failure. Do not revise admission/ordering, source clauses, expected units or thresholds after outputs. Keep canonical/temporal eligibility, constrained syntax, exact navigation, original packet limits and provenance checks. Report any unavailable mode or failed branch in the denominator. Use lexical mode for the first comparison; semantic replication is separately unmeasured.

## Admission diagnosis versus displayed support

Log original and augmented raw candidate file identities, additions, grouped files/ranks, selected/expanded files and bypass reason without adding diagnostic content to the agent-visible packet. For every required source, distinguish: absent before admission; newly admitted but still below selection; selected without required scope; dropped by budget; read without full required text; or verified required text displayed. Gold is read only during scoring, never to select admission, ordering or reads. Required sources entering a pool are a mechanism diagnostic, not successful answers or evidence sufficiency.

## Gates fixed before outputs

Each candidate arm must meet all quality/context gates independently against the same unchanged control:

- At least **two fresh tasks** change from incomplete to complete required-span evidence after the fixed reads, and the affected orientation/current/multi-source/rationale slice improves by at least **five percentage points** on the retained full workload.
- **Zero complete-task losses and zero unit losses** on either the retained controls or fresh confirmation. Every navigation, literal-phrase, temporal, ambiguity, multiple-subject and bounded-unknown case is protected. A scope/name match must not be mistaken for approval, calibration or permission.
- **Zero provenance and response-budget failures.** Same-source required clauses must be displayed in verified canonical ranges; matching a phrase in a different source earns no credit. Source-check changed results and all losses for actual query-bound sufficiency, retaining any disagreement with mechanical scores.
- Total full-interaction tokens increase by at most **5%** over baseline, with unchanged maximum result/read counts and byte caps. Report initial evidence separately from evidence after reads and report per-journey/per-fresh-task outcomes.

Quality failure rejects adoption; do not tune or spend adoption-only runtime integration effort. Passing aggregate evidence or candidate admission alone cannot override a fresh/protected loss. These diagnostics do not measure autonomous answer quality or abstention, and do not establish a comparative efficiency claim.

Only an arm passing quality/context proceeds to quiet-window operating-cost acceptance: warm six fixed representative queries, then at least 20 paired calls with alternating arm order; require recall p95 increase **<=10%** and sampled CPU process-tree peak increase **<=50 MiB**. Record hardware, runtime/QMD identity, process/model/OS cache limits, exact script hash, pair records and index changes. No new model or index is intended; do not imply zero overhead without measuring. Overlapping quality-run timing is observational and cannot satisfy this gate. GPU allocations, Linux/VPS concurrency, human browser utility and independent answer judgments remain outside a local lexical pass.
