- [x] **P2 — Smart search loads the model for every query.** On the VPS (2 vCPU x64, Ubuntu 24.04, Node 22.23.1) every smart search took 6.6–7.1 s, keyword-only about 1.2 s. The search engine runs as a fresh QMD child process per query (see `src/adapters/qmd/qmd.docs.md`), so the 334 MB model is loaded each time; the backend daemon stays at about 80 MB. Measure the Mac (Metal) cost too, then decide between keeping one warm QMD process per root in the backend and documenting the latency in the smart-search explanation.
  Done 2026-11-27. Owner decision: keep the model loaded, because speed matters more than idle memory. The root backend (daemon and `serve`) keeps one warm QMD worker per brain ([qmd-warm.ts](../../src/adapters/qmd/qmd-warm.ts), [qmd-warm-worker.ts](../../src/adapters/qmd/qmd-warm-worker.ts)). It loads the model in the background when the backend starts for a brain whose smart search is ready, and on the first smart search. It unloads after 30 idle minutes; `JUMPYBRAIN_SMART_SEARCH_IDLE_MS` changes this, and `0` keeps the model while the backend runs. At most 2 warm brains per process. Rows are identical to the one-shot `qmd query` CLI. The existing admission, deadline, output-cap and lock rules still apply. Any warm failure kills the worker and falls back with the existing label. Docs: [warm smart search](../../src/adapters/qmd/qmd.docs.md#warm-smart-search), FAQ, install and VPS guides.
  Measured on an Apple Silicon Mac (Metal, Node 26.7, 98 notes):
  - Smart search through the CLI and backend: 1.9–2.3 s before, 0.65–1.0 s after, which is now about the same as keyword search.
  - Model step alone: 1.33–1.40 s cold, 22–46 ms warm.
  - Worker memory while warm: 210–270 MB physical footprint (RSS 760–815 MB, mostly mapped model pages), down to about 120 MB after QMD's own 5-minute context release. The backend itself stays at about 50 MB.
  Verification:
  - Parity: real-model smoke `scripts/semantic-warm-search-smoke.mjs` found identical rows across 90 row sets and 30 end-to-end searches (Metal, CPU and the docs corpus). I reran it on merged master: ok, cold 1328 ms, warm median 22 ms.
  - My own end-to-end run on merged master: first search on a fresh backend 1.5 s, later ones 0.73–1.04 s, no fallback warnings, and the worker exited on `backend stop`.
  - Tests: `test/qmd-warm-search.test.js` (10 cases) and `npm run smoke:semantic-index` pass.
  Not done:
  - VPS (2 vCPU Linux) latency and memory not re-measured.
  - With one `serve` per brain on a VPS, N brains used within 30 minutes hold N models.
  - Windows untested.

- [x] **P2 — Backend from a previous update kept running.** On the owner's Mac a v0.3.27 `daemon.js` (started 2026-11-22 23:28 with the v0.3.27 update) was still alive on 2026-11-25 with no listening socket, no lease and 0 % CPU; the current owner was a different process. It was stopped by hand. Not reproduced on v0.3.28: an idle daemon exits on SIGTERM, and one that served a search and a save exits after losing its lease. Watch for it after the next update (`pgrep -fl dist/server/daemon.js`, compare with `.jumpybrain/backend/owner.json`). A leaked process keeps its runtime generation pinned, which blocks retiring that app version's files.
  Done 2026-11-27 (fixed structurally; the exact leaking handle in v0.3.27 is still unknown).
  What happened: the brain's diagnostics show the v0.3.27 process received the `upgradeOlder` stop at 2026-11-25 12:10:48Z and recorded a clean shutdown and lease release. v0.3.28 started 116 ms later. So the drain finished, and a leftover handle (timer, socket, child or pending I/O) kept Node alive. Ten scenarios exited normally on both v0.3.27 and master. A v0.3.27 daemon with one injected handle reproduced the stuck state.
  Fix: the detached daemon now always exits explicitly when its lifetime ends and logs the kinds of resource still open. A watchdog covers the rest ([server docs](../../src/server/server.docs.md#detached-owner-watchdog)):
  - lost lease or removed root: stop within 1 s
  - unreadable lease, closed listener or stalled check: stop after 5 s
  - not ready within 30 s of winning the lease: stop
  - drain longer than 30 s: forced exit
  The HTTP close now waits for every handler even when one shutdown step fails.
  Checks: `test/backend-daemon-watchdog.test.js` (8 cases) and the backend test files, 101/101 pass.
  Limit: only daemons built from this change onward are covered. Still check `pgrep -fl dist/server/daemon.js` after the next update from v0.3.30.
